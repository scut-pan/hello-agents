# 第八章习题参考答案

本文档对应 [《第八章 记忆与检索》](../../docs/chapter8/第八章%20记忆与检索.md) 的习题，供学习时参考。

> <strong>说明</strong>：本章习题偏向记忆系统设计、RAG 检索策略、遗忘机制和多存储协同。以下答案以“原理理解 + 系统设计 + 工程实现建议”为主，开放题没有唯一标准答案，只要分析完整、方案自洽即可。

## 第 1 题参考答案

### 1. 情景记忆为什么更强调时间近因性，语义记忆为什么更强调图检索

第 8.2.5 节里，两类记忆的评分重点不同：

- 情景记忆：`(向量相似度 × 0.8 + 时间近因性 × 0.2) × 重要性权重`
- 语义记忆：`(向量相似度 × 0.7 + 图检索 × 0.3) × 重要性权重`

这种差异来自它们存储对象的本质不同：

- <strong>情景记忆存的是“发生过什么”</strong>
  - 它强调事件、经历、会话上下文
  - 同样一条语义相近的信息，最近发生的事件通常更值得优先取回
  - 因此加入 `0.2` 的时间近因性，是为了让系统在“相似”之外还知道“新近”
- <strong>语义记忆存的是“知道什么”</strong>
  - 它强调概念、规则、事实、实体关系
  - 对这类知识来说，“关系结构”往往比“发生时间”更重要
  - 因此加入 `0.3` 的图检索，是为了利用知识图谱中的实体、关系和多跳连接

可以这样直观理解：

- 问“我昨天和医生聊过什么”，应该更依赖情景记忆的时间线
- 问“糖尿病和运动管理之间有什么关系”，应该更依赖语义记忆中的知识关系

### 2. “个人健康管理助手”如何组合四种记忆

一个较合理的设计是把四种记忆分别承担不同职责：

#### 工作记忆

存放当前对话和短期任务上下文，例如：

- 今天刚输入的早餐、午餐、步数、睡眠时长
- 当前正在讨论的健康目标，如“本月减重 2kg”
- 当前问诊流程中的临时变量，如“最近三天头痛频率”

它适合快速读写，但不适合长期保存。

#### 情景记忆

存放具体健康事件，例如：

- 2026-06-20 晚上跑步 5 公里后心率过高
- 某次体检结果解读过程
- 某周因熬夜导致连续几天睡眠不足

它适合保留“事情是怎么发生的”，方便回溯行为与结果。

#### 语义记忆

存放稳定的健康知识和用户长期画像，例如：

- “高盐饮食可能增加血压风险”
- “用户乳糖不耐受”
- “用户更适合低冲击有氧运动”
- “空腹血糖偏高时，控制精制碳水摄入更重要”

它负责把零散事件抽象成可复用知识。

#### 感知记忆

存放多模态输入，例如：

- 食物图片识别结果
- 运动手环截图
- 体检报告 PDF/OCR 提取内容
- 睡眠监测图表或心率曲线

它适合处理原始感知数据，并为其他记忆类型提供素材。

#### 一个完整链路

可以设计成：

1. 用户上传午餐照片，进入感知记忆
2. 图片识别出食物与热量，短期保存在工作记忆
3. 该次饮食行为被记录为情景记忆
4. 多次观察后总结出“用户晚餐偏高油高盐”，沉淀为语义记忆

### 3. 重要工作记忆何时整合为长期记忆，如何设计触发条件

工作记忆不应机械地全部保留，否则会迅速膨胀。更合理的做法是满足条件后再整合到长期记忆。

常见触发条件可以包括：

- <strong>高重要性</strong>
  - 例如用户明确说“以后记住我对青霉素过敏”
- <strong>高重复频率</strong>
  - 同类信息多次出现，说明它可能是长期规律
- <strong>任务闭环完成</strong>
  - 一次问诊、一次学习、一轮项目执行结束后，可对关键内容做总结
- <strong>显著影响未来决策</strong>
  - 如长期目标、偏好、约束条件、风险提示

自动整合机制可设计为一个综合触发公式：

`整合分数 = 重要性 × 0.4 + 重复次数得分 × 0.3 + 最近使用频率 × 0.2 + 用户显式要求 × 0.1`

当整合分数超过阈值时：

- 若内容是具体事件，转为情景记忆
- 若内容是稳定规律，进一步总结为语义记忆

例如：

- “用户今天只睡了 4 小时”先保留在工作记忆
- 如果连续 10 天都出现睡眠不足，就应整合出“用户近期存在持续睡眠问题”

## 第 2 题参考答案

### 1. 没有明确标题结构时，如何优化分块策略

当文档没有清晰标题结构时，单纯依赖 Markdown 层级会失效。这时更适合引入“语义边界分块”。

一个实用思路是：

1. 先按句子或自然段切分
2. 为每个句子或段落生成嵌入
3. 计算相邻片段的语义相似度
4. 当相似度突然下降时，认为出现了主题边界
5. 再结合最大长度、最小长度做二次约束

一个简化算法可以写成：

- 相邻相似度高于阈值：继续合并
- 相邻相似度低于阈值：切断
- 若当前块太长：强制切分
- 若当前块太短：与下一块合并

这种方法对小说、法律条文、访谈记录更合适，因为它不依赖显式标题，而依赖语义连续性。

### 2. 基础检索、MQE 和 HyDE 的适用场景对比

以“技术文档问答”为例：

#### 基础检索

特点：

- 速度快
- 实现最简单
- 对用户表达与文档措辞接近的情况效果好

适用：

- FAQ
- 标准术语明确的问题

局限：

- 若用户说法和文档原文差异大，容易漏召回

#### MQE

特点：

- 把一个问题改写成多个查询并并行检索
- 更强的召回能力

适用：

- 用户问题表述模糊
- 同一概念存在多种说法
- 技术文档中英文混杂、术语别名较多

局限：

- 查询次数增多，成本和延迟更高
- 改写质量不佳时会引入噪声

#### HyDE

特点：

- 先生成一段“可能的答案”，再用答案去检索
- 适合缩小“问题语言”和“文档语言”的差距

适用：

- 专业领域知识检索
- 用户只会描述问题，不会给出术语
- 问题比较抽象、开放

局限：

- 假设文档本身可能带偏方向
- 比基础检索更依赖生成模型质量

#### 选型建议

- 追求低成本和低延迟：先用基础检索
- 追求高召回：优先 MQE
- 追求高语义贴合，尤其是专业领域：优先 HyDE
- 线上系统常见做法：基础检索为默认，MQE/HyDE 作为增强模式按需开启

### 3. 三种嵌入方案的评估与选型建议

可以从四个维度比较：

#### 百炼 API

优点：

- 精度通常较高
- 免本地部署
- 适合快速接入

缺点：

- 有调用成本
- 依赖外网与供应商稳定性
- 隐私和合规受限

适合：

- 原型验证
- 中小规模在线应用

#### 本地 Transformer

优点：

- 可离线部署
- 数据可控
- 可针对特定领域做定制

缺点：

- 需要算力和运维
- 冷启动成本较高

适合：

- 企业内网
- 对隐私要求高的业务
- 需要长期稳定运行的系统

#### TF-IDF

优点：

- 极快
- 几乎零成本
- 无需 GPU

缺点：

- 语义能力弱
- 同义词、跨表达方式匹配较差

适合：

- 小规模数据集
- 关键词检索明显的场景
- 作为回退方案

#### 综合建议

- 课程实验和快速验证：API 嵌入或 TF-IDF 回退
- 企业知识库：本地 Transformer 或 API + 本地缓存
- 极低预算场景：TF-IDF 起步，再逐步升级
- 生产级 RAG：优先“语义嵌入 + 结构化过滤”，不要只依赖 TF-IDF

## 第 3 题参考答案

### 1. “智能遗忘”策略如何设计

可以把遗忘从单一规则改为综合评分：

`保留分数 = 重要性 × 0.4 + 访问频率 × 0.25 + 最近访问时间衰减 × 0.2 + 与当前主题相关性 × 0.15`

含义如下：

- 重要性高的记忆更难被遗忘
- 高频访问说明它仍有使用价值
- 长时间未访问的记忆应逐渐降权
- 与当前用户目标高度相关的记忆应保留

执行策略可以是：

- 当容量超限时，删除保留分数最低的一批
- 对接近阈值的记忆先做归档而不是直接删除
- 对敏感信息可走单独清除路径

这比只看时间或只看重要性更接近真实使用场景。

### 2. “记忆归档”机制如何与四种记忆集成

归档不是删除，而是从热存储转到冷存储。

一个可行方案是：

- 工作记忆：一般不归档，优先淘汰或整合
- 情景记忆：长期不访问但保留价值高的事件进入冷存储
- 语义记忆：低频知识可以保留摘要，原始材料归档
- 感知记忆：原始图片、音频、PDF 最适合归档

归档层可以保留：

- 元数据索引
- 摘要信息
- 存储位置指针

检索时先查热层：

- 命中则直接返回
- 若热层分数不够但冷层摘要高度相关，再触发“按需解冻”

这样可以在节省成本的同时，避免彻底失去历史信息。

### 3. 如何确保敏感信息被彻底清除

仅从业务数据库删除通常不够，原因在于：

- 向量数据库里可能还有嵌入副本
- 图数据库里可能还有实体、关系和索引
- 缓存、日志、备份中也可能残留

因此需要“全链路删除”：

1. 删除原始记录
2. 删除对应向量及其 metadata
3. 删除图数据库中的实体、关系和关联索引
4. 清理缓存、副本、搜索索引
5. 记录删除审计日志
6. 对备份建立延迟清除或到期销毁机制

如果对隐私合规要求更高，还应进一步做到：

- 为敏感数据单独打标签
- 写入时保存数据血缘关系
- 删除时按血缘一键追踪全部派生副本

## 第 4 题参考答案

### 1. 何时优先使用 RAG，何时优先使用 Memory，如何做智能路由

一般可以这样区分：

- <strong>优先用 RAG</strong>
  - 查询外部知识库、文档、手册、教材
  - 用户问的是“资料里写了什么”
- <strong>优先用 Memory</strong>
  - 查询用户历史、会话状态、长期偏好、已发生事件
  - 用户问的是“你之前记住了什么”

例如：

- “Transformer 的 self-attention 是什么？”更像 RAG
- “我上次学到哪里了？”更像 Memory

智能路由机制可以按三步做：

1. 先做查询分类
   - 文档知识类
   - 用户历史类
   - 混合类
2. 根据分类分配权重
   - 文档知识类：RAG 70%，Memory 30%
   - 用户历史类：Memory 70%，RAG 30%
   - 混合类：并行检索后重排
3. 用一个轻量判别器或规则引擎做最终路由

触发特征可以包括：

- 是否出现“上次、之前、我学过、我的目标”等记忆词
- 是否出现教材、章节、文档、论文等外部知识词

### 2. 更智能的学习报告生成器如何设计

如果要从“统计信息”升级为“学习分析系统”，可以增加三类能力：

#### 学习轨迹分析

- 用户学了哪些主题
- 每个主题停留了多久
- 哪些内容反复提问

这主要依赖情景记忆和工作记忆。

#### 知识盲点识别

- 哪些概念经常答错
- 哪些章节检索频繁但掌握仍不稳定
- 哪些先修知识缺失

这需要：

- 语义记忆总结用户知识画像
- RAG 检索教材知识结构

#### 下一步推荐

- 推荐复习主题
- 推荐下一章节
- 推荐难度更合适的练习

一个实用方案是：

1. 从情景记忆提取最近学习事件
2. 从语义记忆提炼长期薄弱点
3. 从 RAG 中检索当前章节前后依赖关系
4. 生成“已掌握 / 待巩固 / 下一步建议”三段式报告

### 3. 多用户 Web 服务下的数据隔离与性能优化

用户级隔离的核心是“每条数据都带上用户边界”。

在 Qdrant 中可采用：

- collection 级隔离：每个用户独立 collection，隔离强但运维重
- payload 级隔离：共享 collection，但每条向量带 `user_id`

在 Neo4j 中可采用：

- 节点和关系统一带 `user_id`
- 查询时必须附带用户过滤条件
- 对高安全场景可按库或子图隔离

性能优化可以包括：

- 热门用户或热点查询做缓存
- 按租户分片
- 为 payload 和图属性建立索引
- 对多用户并发检索使用异步和批量请求

工程上通常推荐：

- 中小规模：共享存储 + `user_id` 过滤
- 高安全或大客户场景：独立命名空间甚至独立实例

## 第 5 题参考答案

### 1. 自动抽取实体和关系的准确性风险，以及质量评估机制

自动抽取一定有价值，但准确性不会始终稳定。常见错误包括：

- 实体边界识别错误
  - 把一个长术语切碎，或把两个概念错误合并
- 实体消歧失败
  - 同名不同义的实体被混淆
- 关系方向错误
  - 把“A 影响 B”抽成“B 影响 A”
- 幻觉关系
  - 文本里没有明确表达，但模型强行补出关系

知识图谱质量评估机制可以设计为：

1. <strong>结构层检查</strong>
   - 是否存在孤立节点、异常高连接节点、重复边
2. <strong>语义层检查</strong>
   - 实体类型是否合理，关系是否符合 schema
3. <strong>证据层检查</strong>
   - 每条关系是否能追溯到原文片段
4. <strong>抽样人工复核</strong>
   - 对高影响实体和高频关系做人工审核

如果系统面向生产环境，最好建立：

- 置信度分数
- schema 约束
- 人工纠错回流机制

### 2. 一个纯向量检索难以完成，而图查询擅长的场景

例如做“医学研究助手”时，用户问：

“哪些药物通过影响某条代谢通路，间接作用于某疾病相关蛋白？”

这类问题往往需要：

- 找药物实体
- 找药物作用的通路
- 找通路影响的蛋白
- 找蛋白与疾病之间的关系

这就是典型的多跳关系查询，Neo4j 很适合：

- 路径查找
- 多跳遍历
- 子图约束查询

而纯向量检索更擅长找“语义相似文本”，不擅长精确表达“必须经过哪些关系链路”。

### 3. 哪些查询类型中图检索提升最明显

图检索在以下查询里提升最明显：

- <strong>关系链查询</strong>
  - 例如“A 通过什么影响 B”
- <strong>路径推理查询</strong>
  - 例如“从课程 A 到课程 D 的先修路径是什么”
- <strong>网络中心性查询</strong>
  - 例如“哪个组件是系统依赖的关键节点”
- <strong>实体约束组合查询</strong>
  - 例如“既属于 X 类，又依赖 Y，但不包含 Z 的对象”

具体例子：

- 纯向量检索能找到很多“微服务依赖”相关文档
- 图检索却能直接回答“服务 A 调用链上所有下游依赖有哪些，哪一层最脆弱”

因此更准确的结论不是“图检索替代向量检索”，而是：

- 向量检索负责找“像不像”
- 图检索负责找“连不连、怎么连”
- 混合策略才能兼顾召回与推理
