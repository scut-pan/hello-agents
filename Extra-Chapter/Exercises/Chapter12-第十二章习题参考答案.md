# 第十二章习题参考答案

本文档对应 [《第十二章 智能体性能评估》](../../docs/chapter12/第十二章%20智能体性能评估.md) 的习题，供学习时参考。

> <strong>说明</strong>：本章习题偏向 BFCL、GAIA、LLM Judge 以及持续评估体系设计。以下答案以“评估原理 + 指标设计 + 工程化评测流程”为主，开放题没有唯一标准答案，只要指标与目标一致即可。

## 第 1 题参考答案

### 1. BFCL 和 GAIA 分别评估什么能力，为什么采用不同匹配方式

两者关注的核心能力不同。

#### BFCL

重点评估：

- 是否选对函数
- 参数是否正确
- 多工具调用是否合理

它本质上是在评估“结构化工具调用能力”。

之所以使用 AST 匹配，是因为函数调用表达式的核心在于语法结构，而不是字符表面形式。

例如：

- 参数顺序变化
- 空格不同
- 等价表达式改写

这些表面差异不应导致误判。

#### GAIA

重点评估：

- 多步推理
- 工具使用
- 真实世界任务解决能力
- 文件处理与综合信息整合

它评估的是“通用 AI 助手能力”。

之所以使用准精确匹配，是因为最终答案往往是：

- 数字
- 短字符串
- 列表或名称

它们需要一定归一化，但不一定需要复杂语法树。

#### 两种评估方法的优缺点

AST 匹配：

- 优点：对结构化调用更稳健
- 缺点：对语义正确但结构不同的复杂行为仍有限

准精确匹配：

- 优点：实现简单，适合短答案任务
- 缺点：遇到开放式、语义等价但表述不同的答案时容易不够用

### 2. “智能客服系统”的评估指标设计

可以按能力拆分：

#### 意图理解准确性

- 指标：分类准确率、F1、混淆矩阵
- 方法：构建带标签的客服意图数据集离线评测

#### API 调用正确性

- 指标：工具选择准确率、参数正确率、调用成功率
- 方法：用类似 BFCL 的结构化评估样本

#### 回答友好性和专业性

- 指标：LLM Judge 分数、人工评分、用户满意度
- 方法：建立评分 rubric，定期抽样评估

#### 异常处理鲁棒性

- 指标：异常恢复率、兜底成功率、错误升级率
- 方法：构造 API 超时、数据缺失、用户表达模糊等异常场景

### 3. 三大挑战的解决思路

#### 输出不确定性

解决思路：

- 使用结构化输出约束
- 多次采样取统计结果
- 对开放题引入 LLM Judge 或人工复核

局限：

- 成本会上升
- 仍难完全消除随机性

#### 评估标准多样性

解决思路：

- 分层定义指标
- 区分离线客观指标与在线主观指标
- 建立面向不同场景的 rubric

局限：

- 指标体系更复杂
- 需要持续维护

#### 评估成本高昂

解决思路：

- 用分层评估策略控制频率和规模
- 日常回归使用轻量样本集
- 重大版本再跑全量基准和人工评审

局限：

- 轻量评估可能遗漏边界问题

## 第 2 题参考答案

### 1. 为什么 AST 匹配优于字符串匹配，以及可能的误判

字符串匹配的问题是：

- 太脆弱
- 只要写法稍有变化就可能误判

AST 匹配更合适，因为它比较的是：

- 函数名
- 参数结构
- 参数值语义

而不是字符表面形式。

但 AST 匹配也并非完美，可能出现：

- <strong>假阳性</strong>
  - 结构相同，但实际语义不同
- <strong>假阴性</strong>
  - 两个调用语义等价，但 AST 表达方式差异较大

改进思路可以包括：

- 对参数做更强的归一化
- 加入类型约束检查
- 对多调用序列做依赖关系匹配
- 必要时加入执行结果校验

### 2. BFCL 四类样本如何设计边界测试

这里给出思路而不是唯一题面。

#### simple

- 参数缺省值容易误判的函数
- 单位换算函数
- 同名不同参数类型函数

#### multiple

- 两个函数调用先后强依赖
- 一个调用结果作为下一个调用输入
- 中间一步如果省略就无法完成任务

#### parallel

- 多地区天气同时查询
- 多个订单状态并发获取
- 多张图片同时 OCR

#### irrelevance

- 用户只是闲聊，并不需要工具
- 用户提供的信息已经足够回答
- 工具可用但调用反而会画蛇添足

这类边界样本的目标，是测试模型是否真正理解“什么时候该调工具、怎么调、什么时候不该调”。

### 3. 扩展 BFCL 评估器的建议

如果要支持执行顺序、效率和错误分析报告，可以增加三块能力：

#### 顺序评估

- 把多调用序列解析成依赖图
- 对必须有先后顺序的调用做约束检查

#### 效率评估

- 统计完成任务所需最小调用次数
- 记录模型实际调用次数
- 输出冗余调用率

#### 错误分析报告

- 统计常见错误类别
  - 选错工具
  - 参数缺失
  - 参数类型错误
  - 顺序错误
  - 不该调却调了

这样 BFCL 就能从“对没对”进化到“为什么错、错在哪、效率怎么样”。

## 第 3 题参考答案

### 1. GAIA Level 1/2/3 的差异，以及 Level 4 的设想

大体可以理解为：

#### Level 1

- 任务较直接
- 工具链较短
- 信息整合难度较低

#### Level 2

- 需要更多步骤
- 可能跨多个信息源
- 对中间推理质量要求更高

#### Level 3

- 任务更开放
- 常包含真实世界复杂约束
- 需要更强的工具使用、搜索和综合判断能力

如果设计 Level 4，可以考虑：

- 跨天或长时程任务
- 多模态材料联合分析
- 带不完整信息和冲突证据的任务
- 需要显式计划、验证和错误恢复的任务

### 2. 准精确匹配如何处理答案多样性，以及何时不够用

准精确匹配常见做法包括：

- 大小写归一化
- 去除空格和标点差异
- 数字格式归一化
- 列表排序后再比较

因此像：

- `42`
- `42.0`
- `四十二`

在合理归一化后都可以视为正确。

但它不够用的情况包括：

- 开放式解释题
- 同义表达丰富的自然语言答案
- 需要判断“语义是否等价”而不只是“字面是否近似”

更智能的匹配算法可以设计成两阶段：

1. 先做规则归一化
2. 再对剩余样本使用 LLM Judge 或语义相似度判别

这样既保留效率，也增加对语义等价的容忍。

### 3. “自定义 GAIA 评估集”如何设计

以“金融领域助手”为例，可设计 10 个问题，覆盖：

- Level 1：读取财报字段、回答直接事实
- Level 2：比较两个季度指标变化
- Level 3：结合多份公告、宏观数据和风险因素做综合判断

评估流程建议包括：

1. 为每题准备任务描述
2. 提供标准答案或评分 rubric
3. 标记所需工具类型
4. 运行智能体并记录轨迹
5. 对事实题做规则评估
6. 对综合题加 LLM Judge 或人工复核

重点不是题目数量，而是题型覆盖是否足够真实。

## 第 4 题参考答案

### 1. LLM Judge 的优势与局限

相比纯规则匹配，LLM Judge 的优势是：

- 能理解语义
- 能处理开放式输出
- 能按多个维度同时评价

这让它特别适合：

- 创意写作
- 技术说明
- 复杂问答

但局限也很明显：

- 可能偏好某种文风
- 可能对长答案更宽容
- 评判者本身也有不稳定性
- 不同模型之间标准不完全一致

因此 LLM Judge 很强，但不能被当成绝对真理。

### 2. 三种场景的评分标准设计思路

#### 代码生成质量评估

可设维度：

- 正确性
- 可读性
- 鲁棒性
- 效率

建议把正确性权重设最高，因为代码能不能跑通常是第一位。

#### 创意写作质量评估

可设维度：

- 主题契合度
- 创意性
- 语言表现力
- 结构完整性

这类任务要避免只奖励华丽辞藻，而忽视内容质量。

#### 技术文档质量评估

可设维度：

- 准确性
- 清晰度
- 结构化程度
- 可执行性

尤其要关注：

- 是否有遗漏步骤
- 是否存在误导性描述

### 3. “多评委评估系统”如何设计

如果使用 3-5 个不同 LLM 做评委，可以这样聚合：

1. 所有评委使用同一份评分 rubric
2. 每个评委独立打分并给简要理由
3. 计算平均分、中位数和方差
4. 若分歧过大，触发复评或人工审核

处理分歧的方式可以是：

- 用中位数降低极端值影响
- 对离群评分做异常检测
- 对高争议样本单独列出

这比单一评委更稳，但也更贵。

## 第 5 题参考答案

### 1. “快速评估 / 标准评估 / 全面评估”三层策略如何设计

#### 快速评估

用于日常开发迭代。

可包含：

- 小样本回归集
- 关键路径工具调用测试
- 基础响应延迟统计

特点：

- 便宜
- 快
- 高频运行

#### 标准评估

用于版本发布前。

可包含：

- 中等规模 BFCL / GAIA 子集
- 典型业务场景回放
- LLM Judge 抽样评分

特点：

- 覆盖较全面
- 成本中等

#### 全面评估

用于重大升级或对外发布。

可包含：

- 全量基准测试
- 多轮人工审核
- 异常与对抗场景压力测试
- 长时程任务稳定性测试

特点：

- 最稳
- 最贵

### 2. “持续评估系统”如何设计

一个持续评估系统通常包括：

- 评估任务调度器
- 数据集与样本管理
- 执行器
- 指标存储
- 趋势看板
- 告警模块

告警规则可以设计为：

- 总分连续两次下降
- 某关键指标跌破阈值
- 某类错误占比突然上升
- 响应时间显著恶化

这样不仅能知道“现在表现怎么样”，还能知道“是不是在退化”。

### 3. 面向不同受众的评估报告如何生成

#### 开发者报告

应重点包含：

- 细粒度指标
- 失败样本
- 错误分类
- 模型版本和配置

#### 产品经理报告

应重点包含：

- 任务完成率
- 用户体验相关指标
- 版本对比趋势
- 风险摘要

#### 用户报告

应重点包含：

- 简明结论
- 关键提升点
- 已知限制
- 易懂的图表或等级展示

同一组评估数据，不同报告视角不同：

- 开发者关心怎么修
- 产品关心值不值得发
- 用户关心现在好不好用
