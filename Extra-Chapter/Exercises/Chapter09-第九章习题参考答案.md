# 第九章习题参考答案

本文档对应 [《第九章 上下文工程》](../../docs/chapter9/第九章%20上下文工程.md) 的习题，供学习时参考。

> <strong>说明</strong>：本章习题偏向上下文管理、GSSC 流水线、长时程任务支持工具和渐进式披露。以下答案以“方法论理解 + 系统设计 + 工程落地建议”为主，开放题没有唯一标准答案，只要论证合理即可。

## 第 1 题参考答案

### 1. 什么是“上下文腐蚀”，为什么大窗口不代表可以随便塞内容

“上下文腐蚀”可以理解为：

- 上下文越来越长
- 但真正有价值的信息密度越来越低
- 模型被噪声、重复信息、过时信息干扰，决策质量反而下降

即使模型支持 100K 或 200K 上下文，仍然要谨慎管理，原因包括：

- <strong>注意力资源仍是稀缺的</strong>
  - 并不是所有 token 都能被同等有效地利用
- <strong>旧信息可能过时</strong>
  - 长时任务里，很多早期结论后续已经失效
- <strong>重复信息会稀释重点</strong>
  - 模型可能不断看到相似但略有差异的描述
- <strong>成本和延迟都会上升</strong>
  - 长上下文会显著增加推理成本

所以大窗口的价值是“给我们更大的调度空间”，而不是“允许我们停止管理”。

### 2. 一次性加载全部代码 vs JIT 按需检索

以“代码审查助手”为例，两种策略各有优缺点。

#### 方案一：一次性加载全部文件

优点：

- 上下文完整
- 对全局架构问题更友好
- 适合小型仓库或非常短的分析任务

缺点：

- 成本高
- 噪声多
- 容易让模型把注意力浪费在无关文件上
- 文件一多就会触发上下文腐蚀

#### 方案二：JIT 按需检索

优点：

- 只拿当前需要的信息
- 更节省 token
- 更适合大仓库和长时任务
- 信息更新更及时

缺点：

- 可能遗漏全局依赖
- 检索策略设计不好时会走弯路
- 对工具能力和上下文调度要求更高

#### 适用建议

- 小项目、一次性总览分析：可偏向全量加载
- 大项目、渐进式问题定位：优先 JIT 检索
- 最实用的方案通常是混合式：
  - 先加载项目摘要和目录结构
  - 再按需读取具体文件

### 3. “过度硬编码”和“过于空泛”的实际例子

#### 过度硬编码

例如系统提示写成：

“你必须先读取 `src/main.py`，再读取 `config.yaml`，然后只能用三段式回答，不允许查看其他文件。”

问题在于：

- 把任务路径写死
- 限制了模型对新情况的适应能力
- 一旦项目结构变化就失效

#### 过于空泛

例如系统提示写成：

“你是一个很有帮助的代码助手，请尽量协助用户。”

问题在于：

- 没有边界
- 没有优先级
- 没有输出标准

#### 平衡点

合适的系统提示通常应该：

- 明确角色和目标
- 明确安全边界
- 明确推荐工作流
- 保留一定自主决策空间

例如：

“你是代码审查助手。优先通过目录、关键入口文件和变更文件建立上下文；遇到大仓库时按需读取文件；输出应优先指出风险和回归点。”

这类提示既有方向，也没有把动作完全写死。

## 第 2 题参考答案

### 1. GSSC 某一阶段失效会带来什么后果

GSSC 四个阶段是串联关系，任何一个阶段失效都会影响最终结果。

#### Gather 失效

- 没有收集到关键事实
- 后面再精细选择也没有意义
- 常见后果是“根本没看到正确材料”

#### Select 失效

- 把不相关信息留下来，把关键材料丢掉
- 会直接造成上下文偏航
- 智能体可能回答得很流畅，但方向错了

#### Structure 失效

- 信息虽然对，但组织混乱
- 模型难以抓住重点和依赖关系
- 常见后果是理解碎片化

#### Compress 失效

- 压缩过度：关键信息丢失
- 压缩不足：噪声过多
- 常见后果是“看起来短了，但不够用”或“还是太长”

因此 GSSC 不是简单管道，而是一个需要整体校准的系统。

### 2. “上下文质量评估”功能如何设计

可以在每次构建上下文后，自动输出三个维度的评分：

#### 信息密度

- 单位 token 中包含多少有效事实
- 是否存在大量重复、空话、模板化内容

#### 相关性

- 当前上下文与用户目标的语义相似度
- 不同片段是否真正服务于当前任务

#### 完整性

- 当前任务需要的关键槽位是否齐全
- 例如目标、约束、历史决策、阻塞点是否都出现

一个可行实现是：

1. 定义任务所需的关键字段模板
2. 构建上下文后做规则检查
3. 再用 LLM 或分类器做二次评估
4. 输出改进建议

例如：

- “相关性高，但缺少失败历史”
- “信息完整，但重复内容过多”
- “建议保留最近一次测试结果，删除旧日志片段”

### 3. 什么时候截断或滑动窗口比 LLM 摘要更合适

并不是所有压缩都要靠 LLM。

更适合简单截断或滑动窗口的场景包括：

- 日志流、监控流这类强时序数据
- 对原文措辞极其敏感的内容
- 低成本、高频次的日常处理
- 需要避免摘要幻觉的关键证据材料

一个混合压缩策略可以这样设计：

- <strong>结构化信息</strong>：优先提取字段，而不是总结
- <strong>强时序信息</strong>：优先滑动窗口，保留最近若干轮
- <strong>长篇解释性文本</strong>：使用 LLM 摘要
- <strong>关键证据片段</strong>：原文保留，不做改写

这样可以兼顾：

- 成本
- 准确性
- 可追溯性

## 第 3 题参考答案

### 1. NoteTool 的“笔记自动整理”机制如何设计

一个可行思路是给临时笔记设置“定期整理器”。

触发条件可以是：

- 临时笔记数量超过阈值
- 某个任务结束
- 间隔固定时间自动整理

整理流程可以分为：

1. 聚类相似临时笔记
2. 去重和合并
3. 判断哪些属于阶段性结论
4. 将高价值内容提升为任务笔记或项目笔记
5. 对冗余内容做删除或归档

提升规则例如：

- 影响当前任务执行的，升级为任务笔记
- 影响整个项目方向的，升级为项目笔记
- 仅对一次推理有帮助的，保留为摘要后清理

### 2. TerminalTool 的安全机制是否足够，如何做审批流程

路径验证、命令白名单、权限检查已经覆盖了基础风险，但对高风险环境来说还不够。

额外风险包括：

- 白名单命令组合后仍可能造成破坏
- 读取敏感文件可能泄露秘密
- 看似无害的命令可能造成高资源占用

如果需要访问敏感文件或执行危险操作，可以设计“人机协作审批”流程：

1. 智能体提出操作申请
2. 说明操作目的、目标路径、潜在影响
3. 系统给出风险等级
4. 人类审批后才能执行
5. 执行结果写入审计日志

审批信息至少应包含：

- 谁发起
- 为什么做
- 会影响哪些文件
- 是否可回滚

### 3. “智能代码重构助手”的工作流程

一个完整流程可以概括为：

1. 使用 TerminalTool 探索代码库结构
2. 将关键发现写入项目笔记
3. 识别问题模块并拆成重构子任务
4. 为每个子任务建立任务笔记
5. 执行局部修改、运行验证、记录结果
6. 若失败，记录 blocker 并调整计划
7. 全部完成后汇总为项目总结

如果用流程图表达，可抽象为：

`探索代码 -> 记录发现 -> 制定计划 -> 执行修改 -> 验证结果 -> 更新笔记 -> 继续/回退`

它的关键不是“让智能体自动改代码”，而是让每一步都留痕、可恢复、可追踪。

## 第 4 题参考答案

### 1. 即时访问、会话记忆、持久笔记三层如何协调

这三层可以理解为不同时间尺度的信息系统：

#### 即时访问

- 来源：TerminalTool 等外部即时探索
- 特点：最新、原始、按需获取
- 适合：文件内容、日志、目录结构、实时状态

#### 会话记忆

- 来源：当前会话中已经得到的关键结论
- 特点：比即时访问更抽象，但还偏短期
- 适合：当前任务状态、最近结论、临时假设

#### 持久笔记

- 来源：经过筛选和整理后的长期记录
- 特点：稳定、结构化、可跨会话延续
- 适合：项目计划、里程碑、决策理由、阻塞历史

协调原则是：

- 原始事实尽量留在即时访问层
- 当前推进所需结论放会话记忆
- 跨轮次仍重要的内容写入持久笔记

这样能减少冗余，也能降低三层之间冲突的概率。

### 2. “断点续传”机制如何设计

断点续传的核心是：让系统崩了之后，下一次还能知道“做到哪了、为什么做到这、接下来该干什么”。

笔记中至少要记录：

- 当前目标
- 已完成步骤
- 未完成步骤
- 当前 blocker
- 最近一次关键命令或观察结果
- 下一步建议动作

恢复流程可以是：

1. 加载项目笔记和最近任务笔记
2. 读取最近一次状态快照
3. 用 TerminalTool 验证关键外部状态是否仍成立
4. 如果环境变化明显，先更新笔记再继续执行

也就是说，恢复不能只“读笔记”，还要“校验现实”。

### 3. “任务依赖管理”系统如何与 NoteTool 集成

可以把每个任务建模成带状态的节点：

- `todo`
- `in_progress`
- `blocked`
- `done`

并显式记录依赖关系，例如：

- 任务 B 依赖任务 A
- 任务 D 同时依赖任务 B 和任务 C

与 NoteTool 的集成方式可以是：

- 每个任务笔记都带 `depends_on`
- 项目笔记维护全局任务图
- 当某任务完成时，系统自动检查哪些后继任务可以解锁

这样一来，笔记系统就不只是“记录”，而是轻量任务调度器。

## 第 5 题参考答案

### 1. 一个适合渐进式披露的具体应用场景

以“复杂 Bug 调试”为例。

如果一开始就把所有代码、日志、配置、测试结果全塞进上下文，模型很容易被噪声淹没。渐进式披露的做法是：

1. 先看报错摘要
2. 再看相关模块目录
3. 再打开可疑函数
4. 再查看对应测试和最近变更
5. 必要时再查看更深层依赖

每一步得到的新信息，都会反过来指导下一步探索方向。

这种方式的优势是：

- 更节省上下文
- 更接近真实调试思路
- 更容易在中途纠偏

### 2. 如何设计“探索引导”机制

探索引导的目标，是让智能体避免盲查和过度钻细节。

可用的启发式规则包括：

- 优先看高信息增益的材料
  - 例如入口文件、报错堆栈、最近修改
- 优先验证高风险假设
  - 先排查最可能导致失败的地方
- 限制单路径探索深度
  - 连续三步都没有增量信息就换方向
- 定期做“当前认知总结”
  - 防止一直搜而不收敛

如果再进一步，可以加入元认知问题：

- “我现在缺的是什么信息？”
- “继续深入当前方向还有多大收益？”
- “是否已经足以做出下一步决策？”

### 3. 渐进式披露与一次性全量加载的适用任务对比

渐进式披露明显更有优势的任务：

- 大型代码库调试
- 多轮研究与写作
- 长时程项目推进

原因是这些任务：

- 信息量大
- 目标会演化
- 中途常需要调整方向

一次性加载全部上下文更合适的任务：

- 小规模文本总结
- 简短合同对比
- 篇幅有限的单轮问答

原因是这些任务：

- 范围固定
- 信息量可控
- 不太需要动态探索

因此二者的本质差别是：

- 渐进式披露更适合“边探索边决策”
- 全量加载更适合“材料已知且规模可控”的问题
