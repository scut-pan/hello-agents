# 第十章习题参考答案

本文档对应 [《第十章 智能体通信协议》](../../docs/chapter10/第十章%20智能体通信协议.md) 的习题，供学习时参考。

> <strong>说明</strong>：本章习题偏向 MCP、A2A、ANP 三类协议的定位、组合方式、安全治理和大规模协作设计。以下答案以“协议理解 + 架构设计 + 工程落地建议”为主，开放题没有唯一标准答案，只要系统边界清晰即可。

## 第 1 题参考答案

### 1. 为什么 MCP 强调上下文共享，A2A 强调对话式协作，ANP 强调网络拓扑

三种协议解决的问题层次不同。

#### MCP

MCP 主要解决“智能体如何统一访问外部能力”。

它强调上下文共享，是因为工具调用不只是执行一个函数，更需要把：

- 工具描述
- 资源内容
- 调用结果
- 提示模板

这些信息一起纳入模型可理解的上下文中。它解决的是“工具接入碎片化”的问题。

#### A2A

A2A 主要解决“多个智能体如何像团队一样协作”。

它强调对话式协作，是因为多智能体之间不是简单 RPC，而是：

- 请求
- 澄清
- 分工
- 反馈
- 协商

这样反复往返的过程。它解决的是“角色之间如何协同推进任务”的问题。

#### ANP

ANP 主要解决“当网络里智能体很多时，如何发现、路由和组织它们”。

它强调网络拓扑，是因为：

- 节点很多
- 能力分布不均
- 负载和连通性会影响整体效率

它解决的是“大规模智能体网络的基础设施问题”。

一句话概括：

- MCP 管“接工具”
- A2A 管“谈合作”
- ANP 管“组网络”

### 2. 智能客服系统中三类需求分别选什么协议

题目中的三个需求可以分别映射为：

#### 访问客户数据库和订单系统

优先选 `MCP`。

原因：

- 本质是访问外部工具和资源
- 数据库查询、订单检索、报表接口都适合做成 MCP Server
- 可以统一封装权限、参数验证和审计

#### 多个专业客服智能体协作

优先选 `A2A`。

原因：

- 需要让售后、退款、技术支持等角色互相转交和协商
- 对话式消息比单纯函数调用更合适

#### 支持大规模并发用户请求

优先考虑 `ANP`。

原因：

- 需要服务发现、负载均衡、动态扩容
- 可能要在多个客服智能体实例之间做路由

### 3. 三种协议能否组合使用，以及一个组合场景

当然可以组合，而且现实系统通常就应该组合。

例如设计一个“企业级售后协同平台”：

- 用户请求先进入接待智能体
- 接待智能体通过 A2A 与技术支持智能体、物流智能体协作
- 各个智能体访问数据库、知识库、工单系统时走 MCP
- 整个平台中大量智能体实例通过 ANP 做发现与调度

可抽象为：

`用户 -> 接待 Agent -> A2A 协作 -> MCP 调外部系统 -> ANP 做网络级发现和路由`

职责划分如下：

- MCP：连接 CRM、订单系统、知识库、日志系统
- A2A：负责角色间对话协作
- ANP：负责多实例注册、发现、负载与容错

## 第 2 题参考答案

### 1. 一个新的 MCP 数据分析服务器如何设计

可把服务器拆成三个核心工具：

#### 数据库查询工具

职责：

- 接收受限 SQL 或参数化查询
- 返回结构化结果
- 限制只读权限

#### 数据可视化工具

职责：

- 把查询结果转换成折线图、柱状图、饼图等
- 输出图片文件、图表 JSON 或 Markdown 报告片段

#### 报表生成工具

职责：

- 汇总查询结果和图表
- 生成周报、月报、异常分析摘要

协作流程可以是：

1. 先查数据库
2. 再把结果交给可视化工具
3. 最后由报表工具整合生成最终报告

工程上建议：

- 每个工具边界明确
- 工具输入输出结构化
- 为跨工具流程保留任务 ID，方便审计

### 2. Resources 和 Prompts 的设计目的，以及一个组合场景

MCP 里三种核心能力可以理解为：

- `Tools`：执行动作
- `Resources`：提供可读取的数据
- `Prompts`：提供可复用的提示模板

设计目的分别是：

- Tools 负责“做事”
- Resources 负责“拿材料”
- Prompts 负责“规范怎么做”

一个很适合的场景是“代码审查智能体系统”：

- Resources 提供仓库规范、代码风格手册、历史架构文档
- Prompts 提供“安全审查模板”“性能审查模板”“接口兼容性审查模板”
- Tools 提供读文件、查变更、跑测试、生成报告等能力

这样智能体就不是只会“调工具”，而是同时拥有：

- 可读上下文
- 可复用工作模版
- 可执行动作

### 3. JSON-RPC 2.0 + stdio 的优势、局限和远程扩展思路

当前设计的优势主要有：

- 协议简单
- 本地进程通信开销低
- 开发调试方便
- 与语言实现解耦

局限也很明显：

- 更适合本机或同一运行环境
- 不天然适合跨网络访问
- 鉴权、重试、流控能力较弱
- 大规模部署时不如 HTTP/WebSocket 生态成熟

如果要扩展远程 MCP 服务器，可考虑：

1. 保留 JSON-RPC 消息语义
2. 底层传输改为 HTTP、SSE 或 WebSocket
3. 增加认证、会话管理、超时和重试机制
4. 对长任务支持流式返回和任务状态轮询

也就是说：

- `stdio` 更像本地插件接入形态
- 远程传输更像服务化接入形态

## 第 3 题参考答案

### 1. 给“研究团队”增加 Reviewer 智能体如何设计

一个自然的三方协作流程是：

1. Researcher 收集资料并整理研究要点
2. Writer 把研究要点写成论文初稿
3. Reviewer 从逻辑、结构、证据、表达四个维度评审
4. 若 Reviewer 不通过，则把修改意见发回 Writer
5. 必要时 Writer 再向 Researcher 请求补充证据
6. Reviewer 通过后输出终稿建议

关键点在于：

- Reviewer 不直接写稿，而是负责评价和纠偏
- 修改意见应结构化，比如“问题类型 + 对应段落 + 修改建议”

这类三方机制比两方协作更接近真实团队。

### 2. 冲突解决机制和 A2A 扩展消息类型如何设计

如果两个智能体对同一问题有不同意见，直接覆盖对方并不好。更稳妥的做法是显式引入协商流程。

可新增两类消息：

- `negotiation`
  - 用于陈述分歧点、证据和备选方案
- `voting`
  - 用于在多个候选方案中投票

冲突解决可设计为：

1. 发现分歧
2. 各自提交依据
3. 发起 `negotiation`
4. 若仍无共识，则进入 `voting`
5. 若仍僵持，则交由协调者或人工裁决

这样做的价值是把“冲突”从隐式混乱，变成显式可追踪流程。

### 3. A2A 与 AutoGen、CAMEL 等框架的关系

A2A 更像“协议标准”，AutoGen、CAMEL 更像“上层框架”。

两者关系可以类比为：

- A2A 规定“怎么通信”
- 框架规定“怎么组织智能体行为和控制流程”

因此它们不是完全替代关系，而是可以叠加：

- 框架内部仍可用自己的消息总线
- 对外互联时遵循 A2A

如果要让 A2A 智能体与 AutoGen 智能体通信，可以设计一个桥接层：

- 把 AutoGen 的内部消息结构映射为 A2A `task` / `task_result`
- 把 A2A 收到的任务转换成框架内部 agent message
- 对外暴露标准接口，对内保留框架能力

## 第 4 题参考答案

### 1. 什么时候选星型、网状、分层拓扑，以及规模扩张时如何演进

#### 星型

适合：

- 节点不多
- 管理集中
- 任务以统一入口分发为主

优点：

- 简单
- 易管理

缺点：

- 中心节点容易成为瓶颈和单点故障

#### 网状

适合：

- 节点之间需要频繁直接协作
- 去中心化要求高

优点：

- 灵活
- 局部容错强

缺点：

- 路由复杂
- 网络维护成本高

#### 分层

适合：

- 节点很多
- 角色有明显层次
- 需要区域化或领域化管理

优点：

- 更适合扩展
- 便于治理

缺点：

- 层级设计不当会增加路径长度

当网络从 10 个节点扩展到 1000 个节点时，一般会经历：

- 小规模：星型或轻量分层
- 中规模：分层 + 局部网状
- 大规模：多级分层 + 动态路由 + 区域化自治

### 2. “智能路由算法”如何设计

路由时可综合考虑：

- 任务类型匹配度
- 智能体能力标签
- 当前负载
- 响应延迟
- 历史成功率

一个简单评分公式可以是：

`路由分数 = 能力匹配 × 0.4 + 历史成功率 × 0.2 + 负载余量 × 0.2 + 延迟得分 × 0.2`

调度过程可以是：

1. 先按任务类型筛候选
2. 再按路由分数排序
3. 优先选分数最高的节点
4. 若失败则自动回退到下一候选

这样既考虑能力，也考虑实时状态。

### 3. 关键智能体故障时的容错机制

以“交通管理智能体”故障为例，可设计三层容错：

#### 故障检测

- 心跳检测
- 超时告警
- 异常率监控

#### 备份切换

- 预备热备节点
- 发生故障后自动接管
- 路由层停止向故障节点分发任务

#### 状态恢复

- 定期状态快照
- 关键任务日志持久化
- 恢复后从最近快照继续

如果系统是高价值场景，还应加入：

- 降级策略
- 人工接管入口
- 故障演练机制

## 第 5 题参考答案

### 1. MCP 工具调用的安全风险与权限控制

如果智能体可以随意调用任何工具，风险包括：

- 误删文件
- 执行危险命令
- 越权读取敏感信息
- 被提示注入诱导执行高危操作

权限控制机制建议至少包含：

- 工具级权限
- 参数级校验
- 路径/资源范围限制
- 高危操作人工确认
- 审计日志

例如：

- `read_file` 只能读白名单目录
- `delete_file` 必须人工批准
- `run_command` 只允许有限命令集合

### 2. A2A 和 ANP 的端到端加密方案

一个可行方案是：

1. 每个智能体拥有公私钥对
2. 建立连接时先做身份认证
3. 使用会话密钥加密消息正文
4. 对消息做签名，防止篡改
5. 结合访问控制列表限制不同角色可读内容

这样可以同时保证：

- 机密性
- 完整性
- 身份可信

如果消息要跨多个中继节点转发，还需要明确：

- 中继只看路由头，不看业务正文
- 敏感载荷端到端加密

### 3. 大规模网络中的“信任评估系统”如何设计

可信度可以综合以下因素：

- 历史任务成功率
- 是否频繁超时或失败
- 是否存在异常流量行为
- 协作对象的反馈评分
- 是否多次提供虚假或低质量结果

可以为每个智能体维护一个动态信任分：

`信任分 = 成功率 × 0.4 + 协作评分 × 0.2 + 稳定性 × 0.2 + 安全记录 × 0.2`

使用策略可以是：

- 高信任节点优先参与关键任务
- 低信任节点降低权限和流量
- 极低信任节点进入隔离区或黑名单

这本质上是在大规模智能体网络里建立“身份治理 + 声誉治理”的双重机制。
