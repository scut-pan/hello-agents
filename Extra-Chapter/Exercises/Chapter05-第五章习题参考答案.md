# 第五章习题参考答案

本文档对应 [《第五章 基于低代码平台的智能体搭建》](../../docs/chapter5/第五章%20基于低代码平台的智能体搭建.md) 的习题，供学习时参考。

> <strong>说明</strong>：本章习题偏向平台选型、低代码工程实践、插件与工具扩展，以及平台化与代码化开发的权衡。以下答案以“平台理解 + 工程设计 + 选型建议”为主，开放题没有唯一标准答案，只要方案合理、论证充分即可。

## 第 1 题参考答案

### 1. `Coze`、`Dify`、`FastGPT`、`n8n` 的核心定位和设计理念区别

这四个平台虽然都能做智能体，但出发点并不一样。

#### `Coze`

- <strong>核心定位</strong>：面向低门槛、快速搭建和多平台分发的智能体平台
- <strong>设计理念</strong>：强调“零代码/低代码 + 丰富插件生态 + 快速发布”
- <strong>解决痛点</strong>：
  - 非技术用户难以参与 AI 应用搭建
  - 原型验证速度慢
  - 多平台发布链路复杂

#### `Dify`

- <strong>核心定位</strong>：面向专业开发者和企业的开源 LLM 应用开发平台
- <strong>设计理念</strong>：强调“应用编排 + RAG + Agent + 插件 + 部署能力”的一体化
- <strong>解决痛点</strong>：
  - 企业级应用开发链路分散
  - 从原型到上线缺少统一平台
  - 多模块协作与运维复杂

#### `FastGPT`

- <strong>核心定位</strong>：知识库问答和 RAG 场景优化的平台
- <strong>设计理念</strong>：强调“知识管理、检索、工作流编排、对话系统”的一体化
- <strong>解决痛点</strong>：
  - 企业知识助手搭建门槛高
  - RAG 链路细节多、调试复杂
  - 垂直问答系统难以快速上线

#### `n8n`

- <strong>核心定位</strong>：通用自动化工作流平台，AI 只是其能力之一
- <strong>设计理念</strong>：强调“连接一切系统，并把 AI 嵌入业务流程”
- <strong>解决痛点</strong>：
  - 企业系统之间的数据和动作难以打通
  - 自动化链路需要连接很多 SaaS、数据库、API
  - AI 很难融入现有流程

总结来说：

- `Coze` 更像“快速搭应用”
- `Dify` 更像“搭企业级 AI 产品”
- `FastGPT` 更像“搭知识问答系统”
- `n8n` 更像“搭自动化流程，并把 AI 插进去”

### 2. 低代码、纯代码、混合开发分别适合什么场景

#### 低代码平台

适合：

- 快速原型验证
- 非技术或弱技术团队
- 需求变化快、想尽快上线
- 以工作流和知识库编排为主的项目

例如：

- 企业内部 FAQ 助手
- 活动报名机器人
- 每日 AI 简报助手

#### 纯代码开发

适合：

- 需要高度定制化逻辑
- 对性能、并发、可控性要求极高
- 需要深度集成内部系统且平台抽象不够用
- 需要精细化测试、版本控制和工程治理

例如：

- 高并发智能客服后端
- 自定义多智能体调度框架
- 面向特殊硬件或复杂基础设施的 Agent 系统

#### 混合开发

适合：

- 标准流程部分用平台提高效率
- 核心差异化能力用代码实现
- 团队既想快速上线，又不想失去控制力

例如：

- 用 `Dify` 搭 RAG 和工作流，用代码写内部审批引擎
- 用 `n8n` 串联业务系统，用代码服务做复杂策略决策
- 用 `Coze` 做前台交互，用后端代码实现内部私有工具

所以三种模式不是互斥关系，而是不同抽象层级上的协同选择。

## 第 2 题参考答案

### 1. 如何让 `Coze` 的“每日AI简报”每天早上 8 点自动生成并推送

核心思路是把“用户主动触发”改为“定时触发 + 自动分发”。

可行方案如下：

1. 设置定时任务
   - 如果平台本身支持定时工作流，就直接使用定时调度
   - 如果平台不支持，可通过外部调度器或第三方自动化平台定时调用 Coze API
2. 定时触发智能体生成简报
   - 输入一个固定 prompt，例如“请生成今天的 AI 日报”
3. 将输出结果发送到目标渠道
   - 飞书群：通过机器人 Webhook 或企业应用接口推送
   - 微信公众号：通过公众号消息接口或运营平台中转
4. 加入失败重试和日志记录
   - 避免 RSS 拉取失败或某个插件异常导致整份简报丢失

因此，改造重点不是“改提示词”，而是补上：

- 调度能力
- 推送能力
- 错误恢复能力

### 2. 如何优化简报提示词

可以从以下方向优化：

#### 强化输出结构

明确要求按固定栏目输出，例如：

- 今日头条
- 产业动态
- 学术前沿
- 开源项目
- 热点分析
- 趋势预测

#### 增加质量约束

例如要求：

- 每条内容给出一句话摘要
- 每条内容附原始链接
- 避免营销号标题党风格
- 对重复信息进行去重整合

#### 增加“热点分析”功能

要求模型：

- 识别当天多条新闻中的共同主题
- 总结背后的行业趋势

例如输出：

- “今天 AI 新闻中最显著的趋势是大模型 Agent 化和多模态能力产品化”

#### 增加“趋势预测”功能

要求模型在摘要之后补充：

- “基于今日信息，未来 1-3 个月可能值得关注的方向”

但这里要明确约束：

- 趋势预测必须与当天内容相关
- 需要标明“这是预测，不是事实”

### 3. 什么是 `MCP`，为什么重要，如果 `Coze` 支持会带来什么可能性

`MCP`（Model Context Protocol）可以理解为一种让模型应用与外部工具、资源、提示模板进行标准化连接的协议。

它的重要性在于：

- 统一了工具接入方式
- 统一了资源暴露方式
- 统一了提示模板共享方式
- 让不同平台、不同模型客户端和不同服务端之间更容易互通

从协议能力上看，`MCP` 不只是“调一个工具”，还包括：

- `tools`：可调用能力
- `resources`：可读取资源
- `prompts`：可复用提示模板

如果 `Coze` 未来支持 `MCP`，可能会带来这些变化：

- 能更方便接入外部标准化工具生态
- 能更容易连接企业内部系统、数据库、知识库
- 能减少平台专有插件的绑定成本
- 平台迁移和复用能力更强

也就是说，支持 `MCP` 后，`Coze` 会从“插件平台”进一步走向“标准协议生态平台”。

## 第 3 题参考答案

### 1. `Dify` 中用“问题分类器 + 子智能体”的优势是什么

这种多智能体架构的优势在于“分而治之”。

优势包括：

- 每个子智能体只处理自己擅长的任务，提示词更聚焦
- 不同模块可以分别优化、测试和迭代
- 上下文更短，推理更稳定
- 更利于权限隔离和工具隔离

如果不用分类器，而是让一个单一智能体处理所有任务，常见问题有：

- 提示词过长，职责混乱
- 不同任务之间容易互相干扰
- 工具选择更容易出错
- 某个模块出问题时难定位
- 后续扩展会越来越复杂

因此，多智能体/多模块路由并不是“为了炫技”，而是为了解决复杂系统中的职责分离问题。

### 2. 数据库表很多时，如何更智能地提供表结构信息

如果直接把 50 张表、每张 20 个字段的 DDL 全塞进提示词，上下文一定会过长。

更好的方案是做“按需召回”。

可行设计如下：

1. 建立数据库元数据索引
   - 为每张表保存表名、字段、描述、关联关系、常见查询意图
2. 先做用户问题理解
   - 判断问题大概率涉及哪些业务域
3. 检索最相关的表结构
   - 只把最相关的 3 到 5 张表结构送给模型
4. 必要时二轮扩展
   - 如果模型判断信息不足，再追加更多关联表

还可以进一步结合：

- 表级 RAG
- schema embedding 检索
- 人工维护的业务语义标签

这样做的本质是：<strong>不把数据库全量暴露给模型，而是让模型按需看到最相关结构</strong>。

### 3. `Dify` 本地部署和云端部署的差异

#### 本地部署

优点：

- 数据安全和隐私控制更强
- 更适合敏感行业
- 可根据内部需求做定制

缺点：

- 初始部署复杂
- 需要自己维护升级、监控、备份
- 运维成本更高

适用场景：

- 金融、法律、医疗、政企
- 对私有化和合规性要求高的企业

#### 云端部署

优点：

- 上手快
- 运维负担小
- 更适合快速试验和中小团队

缺点：

- 数据外发需要谨慎评估
- 可控性和定制性通常弱于本地
- 长期调用成本可能上升

适用场景：

- 快速原型验证
- 中小团队先做 MVP
- 对敏感数据要求不高的业务

## 第 4 题参考答案

### 1. `n8n` 如何把内存型存储替换为持久化方案

根据 `n8n` 官方文档，内存型 `Simple Memory` 和 `Simple Vector Store` 并不是唯一选项。

#### 对话记忆

可以改用持久化聊天记忆节点，例如：

- `Redis Chat Memory`
- `Postgres Chat Memory`

大致步骤是：

1. 准备外部存储服务
   - 如 Redis 实例或 Postgres 数据库
2. 在 `n8n` 中创建对应凭据
3. 用持久化记忆节点替换 `Simple Memory`
4. 继续使用统一的 session key / thread id 作为会话标识

#### 向量存储

可以改用：

- `Pinecone Vector Store`
- `Redis Vector Store`

大致步骤是：

1. 准备向量数据库账号或实例
2. 配置 API Key / host / index 名称等参数
3. 在写入阶段把 embeddings 写入持久化向量库
4. 在读取阶段让 AI Agent 工具连接对应的持久化向量库节点

这类替换的关键不在于“节点名字变了”，而在于：

- memory key 要稳定
- embedding 模型要前后一致
- 数据库和索引配置要可持续

### 2. 邮件带附件时如何扩展工作流

如果邮件包含附件，可以把当前文本邮件流程扩展成“邮件正文 + 附件理解”的双通道流程。

例如：

1. 检查是否有附件
2. 如果有 PDF
   - 提取文本
   - 分块
   - 交给模型总结或问答
3. 如果有图片
   - 调用 OCR 或多模态模型识别内容
4. 将附件理解结果与邮件正文一起传给 Agent
5. 生成最终回复

这样系统就不再只回答“邮件里写了什么”，而是能回答“附件里说了什么”。

### 3. 设计一个更复杂的电商自动化场景

可以设计成如下工作流：

```text
Order Trigger
  -> Validate Order
  -> Update Inventory DB
  -> Notify Logistics System
  -> Write CRM Record
  -> Send Confirmation Email
  -> Log Success / Alert on Failure
```

关键配置说明：

- `Order Trigger`
  - 监听电商平台订单创建事件
- `Validate Order`
  - 检查支付状态、库存状态、地址合法性
- `Update Inventory DB`
  - 扣减库存，防止超卖
- `Notify Logistics System`
  - 创建发货任务或同步运单
- `Write CRM Record`
  - 写入客户画像、订单记录、购买偏好
- `Send Confirmation Email`
  - 发送确认通知
- `Error Branch`
  - 如果某一步失败，触发补偿或人工告警

这个例子很好体现了 `n8n` 的优势：它不是单纯“跑一个模型”，而是能把很多业务系统连成一条自动化链。

## 第 5 题参考答案

### 1. `Coze`、`Dify`、`n8n` 的提示词设计有何差异

这些差异和平台特性高度相关。

#### `Coze`

更强调：

- 角色设定
- 输出格式
- 面向最终用户的内容表现

因为它偏向成品型智能体和快速分发。

#### `Dify`

更强调：

- 工作流中的模块职责
- 路由条件
- 结构化输入输出

因为它偏向企业级应用编排和复杂模块协作。

#### `n8n`

更强调：

- 和业务系统、节点上下文的结合
- 工具使用顺序
- JSON 输出格式约束

因为它偏向自动化流程，提示词本质上是工作流中某个决策节点的“控制脚本”。

所以可以这样概括：

- `Coze` 更偏产品化表达
- `Dify` 更偏应用编排逻辑
- `n8n` 更偏流程控制和系统集成

### 2. “输出超过 500 字”这种硬性要求是否合理

这种要求有时合理，有时不合理，取决于任务目标。

合理的情况：

- 希望模型展开论述
- 需要较完整的说明文案
- 需要避免模型输出过于简短

不合理的情况：

- 用户真正需要的是精准、简洁的答案
- 任务本身适合结构化短输出
- 模型为了凑字数而堆砌废话

更好的做法通常不是只限制字数，而是同时约束：

- 输出结构
- 信息完整性
- 语言风格
- 重点覆盖项

例如比“超过 500 字”更好的要求是：

- “分三段输出，每段覆盖具体目标，并给出至少两个实例”

这比单纯拉长字数更能保证质量。

## 第 6 题参考答案

### 1. 如果平台没有所需工具，怎么解决

常见解决方式有三类：

#### 方式一：自己封装 API

把公司内部系统 API 封装成一个中间服务，再接入平台。

#### 方式二：开发自定义插件/节点

- `Dify`：开发自定义插件
- `n8n`：用 HTTP Request / Code 节点，或开发自定义节点
- `Coze`：通过平台支持的插件机制或中间层 API 适配

#### 方式三：通过 `MCP` 暴露能力

如果平台支持 MCP，就把内部系统能力做成 MCP server，让平台按协议接入。

因此，平台没有工具不代表做不了，关键在于你是否愿意：

- 搭中间层
- 开发扩展
- 用标准协议做适配

### 2. `MCP` 与 `RESTful API`、`Tool Calling` 的区别

可以从三个层面理解：

#### `RESTful API`

- 面向通用系统集成
- 关注 HTTP 资源和接口调用
- 不关心模型应用如何理解这些能力

#### `Tool Calling`

- 通常是模型侧能力
- 让模型输出结构化工具调用参数
- 但工具的发现、描述、资源暴露方式往往仍是平台私有的

#### `MCP`

- 是一个面向模型应用生态的开放协议
- 不只定义“怎么调用工具”，还定义：
  - `tools`
  - `resources`
  - `prompts`
- 强调标准化发现、读取和调用能力

为什么说它像“新标准”：

- 它试图把原本各家平台各自定义的工具接入方式统一起来
- 让模型客户端和外部能力服务之间形成更通用的接口层
- 降低生态碎片化问题

所以：

- `REST API` 更像底层通用接口
- `Tool Calling` 更像模型侧调用能力
- `MCP` 更像连接模型应用与外部能力的标准协议层

### 3. 为 `Dify` 开发自定义插件的大致流程

根据 `Dify` 官方文档，开发流程可以概括为：

1. 初始化插件项目

```bash
./dify plugin init
```

2. 配置 `.env`
   - 设置调试所需参数、密钥等

3. 本地运行调试

```bash
python -m main
```

4. 实现插件逻辑
   - 定义插件类型
   - 描述输入输出
   - 调用公司内部知识库 API
   - 处理认证、错误、返回格式

5. 本地测试和联调
   - 确认插件能被 Dify 正常识别和调用

6. 打包发布

```bash
cd ..
dify plugin package ./yourapp
```

关键技术点包括：

- 插件 manifest 与元数据定义
- 输入输出 schema 设计
- 与内部 API 的认证和鉴权
- 错误处理与超时控制
- 本地调试和打包发布流程

本质上，`Dify` 插件开发是在“平台标准接口”和“企业内部能力”之间搭一层适配器。

## 第 7 题参考答案

### 应用 A：面向 C 端的 AI 写作助手小程序

我会优先选择<strong>`Coze` 或者 `Coze + 少量前端封装`</strong>。

#### 理由

- 需要快速上线验证市场
- 团队技术资源有限
- 产品经理也能深度参与
- 多渠道分发和原型迭代速度很重要

#### 维度分析

- <strong>技术可行性</strong>：足够满足 MVP 阶段需求
- <strong>开发效率</strong>：很高
- <strong>成本控制</strong>：前期较好
- <strong>可维护性</strong>：早期可接受
- <strong>可扩展性</strong>：中等，后期可能受平台约束
- <strong>数据安全与合规性</strong>：如果不涉及敏感私有数据，问题不大

### 应用 B：企业级智能合同审核系统

我会优先选择<strong>`Dify` 本地部署`，必要时结合纯代码开发`</strong>。

#### 理由

- 法律文档敏感，要求私有化
- 需要和 OA、文档系统深度集成
- 需要知识库、工作流、插件扩展和权限控制

#### 维度分析

- <strong>技术可行性</strong>：高
- <strong>开发效率</strong>：高于纯代码，但仍保留较强定制能力
- <strong>成本控制</strong>：初期高于云端平台，但长期可控
- <strong>可维护性</strong>：较好，前提是团队具备部署能力
- <strong>可扩展性</strong>：强
- <strong>数据安全与合规性</strong>：最符合需求

### 应用 C：内部研发效能提升工具

我会优先选择<strong>`n8n + 纯代码服务` 的混合模式</strong>。

#### 理由

- 这是典型的多系统自动化问题
- 需要打通代码仓库、测试系统、Bug 系统、项目管理工具、消息通知系统
- `n8n` 擅长连接流程，代码擅长处理复杂逻辑

#### 维度分析

- <strong>技术可行性</strong>：高
- <strong>开发效率</strong>：对这类流程整合非常高
- <strong>成本控制</strong>：取决于自建规模，但通常合理
- <strong>可维护性</strong>：流程可视化有优势，但复杂逻辑最好下沉到代码服务
- <strong>可扩展性</strong>：强
- <strong>数据安全与合规性</strong>：内部部署下较好

### 综合结论

如果把这三类应用放在一起看，会发现平台选型的核心不是“哪个平台最好”，而是“哪个平台最符合当前业务阶段和约束条件”：

- 面向 C 端、追求快：优先低门槛平台
- 面向企业、追求稳：优先可私有化平台
- 面向内部自动化、追求连接能力：优先工作流平台

这也是低代码平台真正的价值所在：它们不是统一答案，而是不同问题空间中的不同高效解法。
