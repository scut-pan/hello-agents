# 第四章习题参考答案

本文档对应 [《第四章 智能体经典范式构建》](../../docs/chapter4/第四章%20智能体经典范式构建.md) 的习题，供学习时参考。

> <strong>说明</strong>：本章习题偏向架构设计、工程实现与系统权衡。以下答案以“范式理解 + 工程思路 + 可落地建议”为主，开放题没有唯一标准答案，只要设计合理、论证清晰即可。

## 第 1 题参考答案

### 1. `ReAct`、`Plan-and-Solve`、`Reflection` 在“思考”与“行动”组织方式上的本质区别

三者的核心区别可以概括为：

- <strong>`ReAct`</strong>：边思考边行动。
  它强调 `Thought -> Action -> Observation` 的交替循环，适合在执行过程中不断根据环境反馈调整策略。
- <strong>`Plan-and-Solve`</strong>：先整体规划，再分步执行。
  它把“想清楚”放在前面，先生成完整计划，再严格按计划求解，强调结构性和稳定性。
- <strong>`Reflection`</strong>：先执行，再反思，再优化。
  它关注结果质量提升，不一定改变任务分解方式，但会通过“执行-反思-改进”的迭代让结果越来越好。

如果用一句话来区分：

- `ReAct` 解决的是“边做边看怎么做”
- `Plan-and-Solve` 解决的是“先想好再做”
- `Reflection` 解决的是“做完以后怎么做得更好”

### 2. 设计“智能家居控制助手”时，更适合哪种范式

如果是“控制灯光、空调、窗帘，并根据用户习惯自动调节”的场景，我会优先选择<strong>`ReAct` 作为基础架构</strong>，再辅以一定的计划和反思能力。

原因如下：

- 智能家居场景是<strong>强环境交互</strong>型任务。
- 智能体需要实时感知环境状态，例如室温、光照、是否有人、用户是否刚发出新指令。
- 执行某个动作后，还要根据设备返回值或环境变化继续调整。

这些特点都非常符合 `ReAct` 的优势：

- 先判断当前状态
- 再调用设备控制工具
- 再观察设备执行结果和环境反馈
- 再决定下一步动作

例如：

- 用户说“有点热”
- 智能体先查询当前室温与空调状态
- 决定调低空调温度
- 再观察是否执行成功
- 若失败则重试或切换备用设备控制方式

相比之下：

- 纯 `Plan-and-Solve` 更适合任务路径比较确定的场景
- 纯 `Reflection` 更像质量增强层，不适合单独做实时控制主循环

### 3. 三种范式能否组合使用

可以，而且在真实系统中往往更推荐组合使用。

一个可行的混合架构如下：

#### 第一层：`Plan-and-Solve` 做高层规划

当用户提出较复杂目标时，例如：

- “我今晚 8 点看电影时，把客厅调成观影模式”

智能体先规划高层步骤：

- 识别场景目标
- 确认时间约束
- 确定需要控制的设备
- 形成场景配置方案

#### 第二层：`ReAct` 做实时执行

到了执行时刻，智能体再进入 `ReAct` 循环：

- 查询灯光状态
- 调整亮度
- 拉上窗帘
- 调低空调风速
- 播放指定背景音

每一步都根据设备反馈动态修正。

#### 第三层：`Reflection` 做事后优化

任务执行后，系统再反思：

- 用户是否频繁手动改回设置
- 某些设备控制是否经常失败
- 当前推荐的“观影模式”是否真的符合用户偏好

并据此优化后续策略。

#### 适用场景

这种混合范式特别适合：

- 智能家居
- 企业流程自动化
- 电商客服
- 旅行规划与执行

因为这些场景往往既需要计划，也需要实时交互，还需要长期优化。

## 第 2 题参考答案

### 1. 当前正则解析方法有哪些脆弱性

使用正则表达式解析 `Thought` / `Action` 的主要问题在于，它对输出格式过于敏感。

典型脆弱性包括：

- 模型没有严格按预期格式输出
- `Thought:` 或 `Action:` 拼写发生变化
- 输出中出现多余换行、注释、Markdown 包裹
- 一个回答中出现多个 `Action`
- `Action` 参数里本身含有括号、引号或特殊字符
- 模型同时输出自然语言解释和结构化字段，导致正则匹配歧义

例如：

- 模型输出了 ```````markdown` 包裹内容
- 模型把 `Action:` 写成了 `Next Action:`
- 模型生成了嵌套括号参数

这些都可能让正则解析失败。

### 2. 更鲁棒的输出解析方案有哪些

比正则更稳的方式通常包括：

- <strong>JSON 输出</strong>：
  要求模型返回固定字段，例如 `{"thought": "...", "action": "...", "input": "..."}`。
- <strong>函数调用 / Tool Calling</strong>：
  直接使用模型原生工具调用能力，让模型输出结构化工具调用而不是自由文本。
- <strong>XML / YAML 等带标签结构</strong>：
  相比纯自然语言更容易解析。
- <strong>Pydantic / JSON Schema 校验</strong>：
  在解析后再做结构校验，发现字段缺失或类型错误时触发重试。

其中最推荐的是：

- 如果模型支持原生 tool calling，就优先用 tool calling
- 如果不支持，就用 JSON + schema 校验

### 3. 尝试改成更可靠的输出格式，并比较优缺点

一个可行改法是把输出格式改成 JSON，例如：

```json
{
  "thought": "我需要先搜索华为最新手机信息",
  "action": "Search",
  "action_input": "华为最新手机是哪一款"
}
```

或者任务结束时：

```json
{
  "thought": "信息已经足够，可以给出最终回答",
  "action": "Finish",
  "action_input": "华为最新手机是……"
}
```

#### 正则方案优点

- 实现简单
- 易于教学演示
- 不依赖模型高级能力

#### 正则方案缺点

- 容易因为格式漂移失败
- 扩展复杂字段时很脆弱
- 难做严格校验

#### JSON 方案优点

- 结构清晰
- 更容易程序解析
- 可配合 schema 做自动校验和重试

#### JSON 方案缺点

- 对提示词要求更高
- 某些模型仍可能输出不合法 JSON
- 教学初期比正则略复杂

综合来看：

- 教学演示：正则足够直观
- 真实系统：JSON 或原生 tool calling 更值得采用

## 第 3 题参考答案

### 1. 为 `ReAct` 智能体添加“计算器”工具

可以新增一个 `Calculator` 工具，例如：

```python
def calculator(expression: str) -> str:
    """
    安全地计算数学表达式。
    """
    try:
        allowed_chars = "0123456789+-*/(). "
        if not all(ch in allowed_chars for ch in expression):
            return "错误: 表达式包含非法字符。"
        result = eval(expression, {"__builtins__": {}}, {})
        return str(result)
    except Exception as e:
        return f"计算错误: {e}"
```

再注册到 `ToolExecutor`：

```python
toolExecutor.registerTool(
    "Calculator",
    "一个数学计算工具。当你需要做精确算术运算时使用此工具。",
    calculator
)
```

这样，对于 `"(123 + 456) * 789 / 12"` 这种问题，智能体就可以优先调用计算器，而不是只靠语言模型心算。

### 2. 如何处理“工具选择失败”

可以设计一个多层纠错机制：

#### 记录失败次数

为每次工具调用记录：

- 工具名
- 输入参数
- 失败原因
- 同类失败累计次数

#### 把错误反馈给模型

例如给 Observation 返回：

- `工具不存在`
- `参数格式错误`
- `该工具不适合当前任务`

并提示模型重新选择工具。

#### 设置失败阈值

如果连续两到三次调用失败，可以触发额外提示，例如：

- “你可能选择了错误的工具，请重新审视当前任务需求”
- “当前任务更适合使用 Search/Calculator，而不是 EmailSender”

#### 启用兜底策略

例如：

- 自动退回到高层规划
- 请求模型先输出工具选择理由
- 触发人工接管或安全退出

因此，工具失败处理不应只是“报错”，而应设计成一个<strong>带反馈的纠错回路</strong>。

### 3. 当工具数量增加到 50 或 100 个时，如何优化组织和检索机制

当工具数量很多时，当前“把所有工具描述直接塞进提示词”的方式会越来越低效。

问题包括：

- 提示词过长
- 模型注意力分散
- 容易选错工具
- 工具维护成本高

更好的工程方案包括：

#### 工具分组

按功能分类，例如：

- 搜索类
- 计算类
- 数据库类
- 通讯类
- 设备控制类

先让模型选“工具组”，再选具体工具。

#### 工具检索

把工具描述做向量化或关键词索引，根据当前任务先召回最相关的 3 到 5 个工具，再交给模型选择。

#### 工具元数据设计

每个工具增加结构化标签，例如：

- 适用任务类型
- 输入参数模式
- 风险级别
- 是否只读 / 是否会修改外部状态

#### 安全与权限分层

高风险工具不应与普通工具平等暴露，应该按权限或审批流程限制。

因此，当工具规模变大时，系统设计重点会从“如何让模型知道所有工具”转向“如何高效召回最相关工具”。

## 第 4 题参考答案

### 1. 如何设计“动态重规划”机制

如果 `Plan-and-Solve` 在执行过程中发现某一步失败，最自然的做法就是把“执行结果”重新反馈给规划模块，让它局部更新计划。

一个可行机制如下：

1. 先生成初始计划
2. 执行每一步时记录结果
3. 一旦某步失败，暂停执行
4. 将以下信息重新交给规划模块：
   - 原始目标
   - 原计划
   - 当前已完成步骤
   - 失败步骤
   - 失败原因
5. 让模型只对“剩余未完成部分”重新规划

这样就形成了：

- 初始规划
- 执行
- 异常检测
- 局部重规划
- 继续执行

这种方式可以避免一失败就完全推翻整个计划，也比纯静态计划更适合真实世界任务。

### 2. 预订北京到上海商务旅行时，`Plan-and-Solve` 和 `ReAct` 哪个更合适

这个任务里，我会更倾向于<strong>`ReAct` 或者“Plan-and-Solve + ReAct”混合方案</strong>。

原因是：

- 旅行预订看起来适合规划，但其实环境变化很强
- 机票、酒店、租车信息都可能实时变化
- 某个选项可能临时售罄、涨价或不符合约束

如果只用纯 `Plan-and-Solve`：

- 计划一旦建立，很容易在执行时失效

如果只用纯 `ReAct`：

- 又可能陷入局部决策，缺少全局安排

因此更合适的是：

- 先用 `Plan-and-Solve` 确定高层步骤
- 再用 `ReAct` 执行每个具体预订动作，并根据实时反馈调整

### 3. 分层规划系统的设计与优势

一个“分层规划”系统可以这样设计：

#### 高层计划

- 确定出行时间
- 预订机票
- 预订酒店
- 预订租车
- 输出完整行程单

#### 子计划

例如对“预订酒店”再细分：

- 筛选商圈
- 筛选预算范围
- 比较评分与距离
- 检查可取消政策
- 完成预订

#### 优势

- 更容易处理复杂任务
- 高层结构更稳定，低层执行更灵活
- 某个子任务失败时，只需局部重规划
- 更接近人类做复杂任务时的组织方式

所以分层规划的本质优势是：<strong>既保留全局结构，又保留局部灵活性</strong>。

## 第 5 题参考答案

### 1. 用不同模型分别做执行和反思，会有什么影响

这是一个非常实际的优化方向。

例如：

- 用较快、较便宜的模型做初始执行
- 用较强、较贵的模型做反思

可能带来的好处：

- 降低总体成本
- 保持较好的响应速度
- 把高质量分析能力集中用在最关键的反思环节

但也会带来挑战：

- 两个模型风格不同，可能导致反馈和执行不一致
- 强反思模型提出的修改建议，弱执行模型未必能很好落实
- 系统调试复杂度更高

因此，这种“双模型 Reflection”很有价值，但需要额外设计：

- 统一输出格式
- 控制反馈粒度
- 增加执行后校验

### 2. 当前终止条件是否合理，能否更智能

“出现 `无需改进` 或达到最大迭代次数”是一个可用的基础方案，但并不够智能。

问题在于：

- 模型可能过早判断“无需改进”
- 模型可能一直提出微小修改，导致无意义迭代

更智能的终止条件可以综合多个信号：

- 反思反馈严重程度是否明显下降
- 连续两轮改动收益是否很小
- 外部评估指标是否已经达到阈值
- 结果是否通过测试、校验或评分器评估

例如代码生成场景中，可以加入：

- 单元测试全部通过
- 性能指标达到目标
- 风格检查通过

只有当这些外部指标和反思判断都满足时再停止，会比只看一句“无需改进”更可靠。

### 3. 为“学术论文写作助手”设计多维度 Reflection 机制

可以把反思拆成多个维度，每个维度由不同提示词或不同评审角色负责。

#### 维度一：段落逻辑性

关注：

- 段落之间是否衔接自然
- 论证是否层层推进
- 是否存在跳步和重复

#### 维度二：方法创新性

关注：

- 方法是否只是已有工作的简单堆叠
- 是否明确指出与现有工作的区别
- 创新点是否足够聚焦

#### 维度三：语言表达

关注：

- 表达是否清晰、学术化、简洁
- 是否存在模糊表述或口语化句子

#### 维度四：引用规范

关注：

- 是否有结论缺少引用支持
- 引用是否与论述一致
- 是否混淆了不同文献结论

#### 工作流

可以设计成：

1. 先生成初稿
2. 分别从 4 个维度做反思
3. 汇总各维度反馈
4. 生成修订版本
5. 再做一轮总评

这类多维 Reflection 的核心思想是：

- 不让模型只做“泛泛而谈的自我批评”
- 而是让它在多个明确维度上做结构化评审

## 第 6 题参考答案

### 1. `ReAct` 提示词和 `Plan-and-Solve` 提示词的结构差异如何服务于范式逻辑

`ReAct` 的提示词强调：

- 当前问题
- 可用工具
- 输出格式必须包含 `Thought` 和 `Action`
- 根据观察结果继续下一轮

这说明它服务的是<strong>交互式循环决策</strong>。

而 `Plan-and-Solve` 的提示词更强调：

- 先生成步骤化计划
- 按计划逐步执行
- 保持任务结构完整

这说明它服务的是<strong>先规划后执行</strong>的逻辑。

所以提示词结构不是表面差异，而是对范式本质的直接映射：

- `ReAct` 的提示词在教模型“如何循环行动”
- `Plan-and-Solve` 的提示词在教模型“如何先构造全局路径”

### 2. 改变 `Reflection` 角色设定，会对输出产生什么影响

如果把角色从“极其严格的代码评审专家”改成“注重代码可读性的开源项目维护者”，输出通常会发生明显变化。

可能的变化包括：

- 更少关注算法极限性能
- 更关注命名、注释、函数拆分、可维护性
- 更倾向于提出风格和结构优化建议

这说明角色设定会显著影响：

- 模型关注的问题维度
- 评价标准
- 最终优化方向

本质上，角色设定相当于给模型指定了“评审视角”。

### 3. 给某个智能体加入 `few-shot` 示例，并比较效果

以 `ReAct` 为例，可以加入一个小示例：

```text
Question: 今天天津天气怎么样？
Thought: 我需要调用搜索工具获取实时天气信息。
Action: Search[今天天津天气]
Observation: 天津今天多云，28摄氏度。
Thought: 我已经拿到天气信息，可以回答用户。
Action: Finish[天津今天多云，气温28摄氏度。]
```

加入 few-shot 后的常见效果：

- 更容易严格遵循 `Thought/Action` 格式
- 更少出现自由发挥的额外文字
- 工具调用意图更明确

缺点是：

- 提示更长
- 示例设计不当可能让模型被错误模式束缚

因此，few-shot 的主要价值在于：<strong>让格式、风格和推理路径更稳定</strong>。

## 第 7 题参考答案

### 1. 这个电商客服系统应选择哪种范式

我会选择<strong>`Plan-and-Solve + ReAct + Reflection` 的混合架构</strong>。

理由如下：

- 客服任务本身是有流程的，适合先规划
- 查询订单、物流、发邮件等需要调用工具，适合 `ReAct`
- 对于争议退款单，还需要反思和更审慎判断，适合 `Reflection`

一个可行流程是：

1. `Plan-and-Solve`：
   先把任务拆成“理解诉求 -> 查询订单 -> 查询物流 -> 对照政策 -> 做决策 -> 生成回复 -> 发邮件”
2. `ReAct`：
   对每一步调用相应工具并根据结果继续行动
3. `Reflection`：
   当置信度低或冲突信息较多时，对当前决策做一轮审慎复核

### 2. 这个系统需要哪些工具

至少可以有以下工具：

- `OrderLookup`
  功能：根据订单号查询商品信息、下单时间、支付状态、售后状态
- `LogisticsQuery`
  功能：查询包裹物流状态、签收情况、异常记录
- `PolicyRetriever`
  功能：检索公司退款政策、特殊商品规则、时效限制
- `EmailSender`
  功能：向用户发送结构化回复邮件
- `CaseEscalation`
  功能：把高争议工单转交人工审核

### 3. 如何设计提示词，确保既符合公司利益又保持友好

提示词里需要明确规定几个原则：

- 必须优先依据公司政策和订单事实做决策
- 不得编造规则或擅自承诺政策外补偿
- 回复语气必须礼貌、清晰、有同理心
- 当政策不支持退款时，也要解释原因并提供替代建议
- 当信息不足时，优先请求补充信息，而不是武断拒绝或同意

因此，提示词不应只强调“服务好用户”，也不能只强调“维护公司利益”，而要同时加入：

- 决策依据约束
- 语气约束
- 风险升级条件

### 4. 上线后可能面临哪些风险，如何降低

可能的风险包括：

- <strong>误判退款</strong>：造成直接经济损失
- <strong>过度拒绝</strong>：损害用户体验和品牌形象
- <strong>幻觉式回复</strong>：编造政策、物流信息或处理结果
- <strong>工具调用错误</strong>：查错订单、发错邮件
- <strong>高争议案件处理不当</strong>：引发投诉升级
- <strong>隐私和合规风险</strong>：泄露用户订单或联系方式

对应技术措施包括：

- 用 RAG 或规则检索固定政策，避免自由编造
- 对关键决策加入规则校验层
- 对高风险案件触发人工审核
- 对邮件发送等外部动作设置确认机制
- 做完整日志记录与可追溯审计
- 设置权限控制和敏感信息脱敏

总结来说，这类系统真正上线时的关键不只是“能回答”，而是：

- 能基于事实回答
- 能基于规则决策
- 能在不确定时及时收敛到安全路径

这也是现代 Agent 工程和简单聊天机器人的本质区别。
