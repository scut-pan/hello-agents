# 第一章习题参考答案

本文档对应 [《第一章 初识智能体》](../../docs/chapter1/第一章%20初识智能体.md) 的习题，供学习时参考。

> <strong>说明</strong>：以下答案以帮助理解核心概念为目标。部分题目属于开放题，没有唯一标准答案，只要分析逻辑清晰、论证合理即可。

## 第 1 题参考答案

### 1. `case A`：一台符合冯·诺依曼结构的超级计算机

它通常<strong>不属于智能体</strong>。

理由如下：

- 它虽然具备极强的计算能力，但“算力强”不等于“智能体”。
- 如果只是一个通用计算平台，它本身并不会主动感知环境、设定目标并采取行动。
- 它更像是智能体运行所依赖的基础设施或硬件载体，而不是智能体本身。

补充说明：

- 如果这台超级计算机上运行了一个能够感知环境、做出决策并执行行动的系统，那么“运行在其上的系统”可以是智能体，但“超级计算机硬件本身”不是。

### 2. `case B`：特斯拉自动驾驶系统

它属于<strong>智能体</strong>。

可以从多个维度分析：

- 从内部决策架构看，它至少属于<strong>基于模型的智能体</strong>。
  原因是系统不仅依赖当前传感器输入，还要维护对道路、车辆、障碍物等状态的内部表示。
- 从时间与反应性看，它主要属于<strong>反应式智能体</strong>，同时也带有一定<strong>混合式智能体</strong>特征。
  在紧急避障场景中，它必须在毫秒级快速响应，因此反应性非常强；但在正常驾驶中，它也会进行路径规划、车道选择等较长时程决策。
- 从是否具备学习能力看，若其模型通过大量数据训练和迭代优化，也可视为包含<strong>学习型智能体</strong>成分。

判断理由：

- 它有明确的传感器，如摄像头、雷达、超声波等。
- 它有明确的执行器，如转向、制动、加速控制。
- 它需要围绕“安全驾驶、到达目的地”等目标自主决策。
- 它与环境构成持续的感知-决策-行动闭环。

### 3. `case C`：AlphaGo

它属于<strong>智能体</strong>。

可以从多个维度分析：

- 从内部决策架构看，它接近<strong>基于目标的智能体</strong>和<strong>基于效用的智能体</strong>。
  它的目标是赢得对局，同时会评估不同局面对胜率的影响，本质上是在最大化获胜概率。
- 从时间与反应性看，它是典型的<strong>规划式智能体</strong>。
  它需要评估局面、搜索未来多步走法，并从大量候选策略中选择最优行动。
- 从学习能力看，它也是典型的<strong>学习型智能体</strong>。
  AlphaGo 及其后续版本依赖监督学习、强化学习和自我博弈不断提升能力。
- 从知识表示看，它更偏向<strong>亚符号主义 AI</strong>，因为核心能力主要来自深度神经网络学习到的模式表示。

判断理由：

- 它能够感知棋盘状态。
- 它会基于目标进行规划和决策。
- 它的行动会改变环境，也就是棋局状态。
- 它具备明显的自主决策与学习能力。

### 4. `case D`：ChatGPT 扮演的智能客服

它属于<strong>智能体</strong>，但前提是它不仅生成文本，还能调用工具、查询信息并基于结果继续行动。

可以从多个维度分析：

- 从内部决策架构看，它接近<strong>基于目标的智能体</strong>。
  目标是解决用户问题、完成售后服务、提升用户满意度。
- 从时间与反应性看，它通常属于<strong>混合式智能体</strong>。
  一方面它需要实时响应用户输入，另一方面又要进行多步分析、查询和方案生成。
- 从知识表示看，它更接近<strong>神经符号混合式</strong>。
  大语言模型提供神经网络的语言理解与生成能力，订单查询、规则调用、流程执行等又体现出符号化和工具化的一面。
- 如果系统能够根据历史交互持续优化策略，也可视为包含一定<strong>学习型智能体</strong>特征。

判断理由：

- 它通过用户输入、订单系统、知识库等感知环境。
- 它通过回复、调用接口、提交工单等方式作用于环境。
- 它需要围绕“解决投诉”这一目标进行多步推理和行动。

如果只是一个纯聊天机器人，只会根据上下文生成安慰性文本、不能调用工具或执行外部操作，那么它更接近“语言模型应用”，智能体属性会较弱。

## 第 2 题参考答案

### 1. PEAS 模型描述

#### `P`：Performance（性能度量）

- 用户是否安全完成训练，是否避免过度训练或受伤风险
- 训练目标达成度，如减脂效果、肌肉增长、耐力提升
- 训练计划的个性化程度与执行完成率
- 动作纠正的准确率与实时性
- 饮食建议的合理性、可执行性和持续性
- 用户满意度、留存率和长期健康改善情况

#### `E`：Environment（环境）

- 用户所处的运动环境，如健身房、家庭、户外跑步场景
- 用户身体状态，如心率、疲劳程度、既往伤病、睡眠情况
- 可穿戴设备和传感器数据环境
- 外部环境因素，如天气、温度、器械可用性、噪声等
- 用户的长期健身目标、日程安排和饮食习惯

#### `A`：Actuators（执行器）

- 实时语音提示与鼓励
- 屏幕上的动作指导、训练计划推送和提醒
- 动态调整训练强度、组数、时长和休息时间
- 生成训练报告和饮食建议
- 必要时触发风险预警，如建议立即停止训练或降低强度

#### `S`：Sensors（传感器）

- 心率、血氧、步频、速度、卡路里等可穿戴设备数据
- 加速度计、陀螺仪等动作捕捉数据
- 摄像头或手机视频带来的姿态识别信息
- 用户主动输入的信息，如体重、饮食、疲劳感、目标偏好
- 历史训练记录和健康档案

### 2. 任务环境特性分析

- <strong>部分可观察</strong>：系统无法完整获取用户身体内部状态，例如真实疲劳程度、潜在伤病、情绪状态等。
- <strong>随机性</strong>：同样的训练计划在不同日期、不同身体状态下效果可能不同，环境并非完全确定。
- <strong>动态性</strong>：用户心率、动作质量、体能状态会在训练过程中持续变化，系统必须实时响应。
- <strong>序贯性</strong>：当前决策会影响后续状态，例如前几组训练过强会影响后面动作质量与安全性。
- <strong>连续性</strong>：心率、速度、力量输出等很多变量是连续变化的，而不是离散状态。
- <strong>多目标性</strong>：既要追求训练效果，也要兼顾安全、体验、可持续性和个性化。
- <strong>人机协作性</strong>：用户不是被动环境，而是会反馈、拒绝、调整目标，因此该环境带有强交互性。

总结来说，“智能健身教练”面对的是一个<strong>部分可观察、随机、动态、序贯、连续且多目标的人机交互环境</strong>，因此它更适合采用带有内部状态建模、实时反馈和长期规划能力的智能体架构。

## 第 3 题参考答案

### 1. 方案 A（Workflow）的优缺点

优点：

- 规则明确，容易实现与维护
- 决策过程透明，可解释性强
- 响应速度快，处理成本低
- 便于审计、合规与责任追踪
- 对高频、重复、规则稳定的退款场景非常适合

缺点：

- 缺乏灵活性，难以处理复杂例外情况
- 当规则很多时，流程会迅速变得冗长和脆弱
- 难以利用非结构化信息，如用户情绪、商品图片描述、异常历史行为模式
- 一旦业务政策变化，需要频繁人工改规则

### 2. 方案 B（Agent）的优缺点

优点：

- 能处理更复杂、更模糊的退款情境
- 可以综合政策文本、用户历史、商品状态、客服对话等多源信息
- 具备一定的推理能力和适应能力
- 对例外情况、争议案例、个性化处理更有优势

缺点：

- 可解释性通常弱于固定流程
- 输出存在不稳定性，可能出现误判或幻觉
- 在高风险业务中，直接自主审批可能带来合规和资金风险
- 成本通常更高，系统设计、监控与评估都更复杂

### 3. 什么时候 `Workflow` 更合适，什么时候 `Agent` 更有优势

`Workflow` 更合适的情况：

- 退款政策清晰且较稳定
- 业务量很大，追求低成本和高吞吐
- 风险控制和审计要求高
- 大多数申请都属于标准化场景

`Agent` 更有优势的情况：

- 退款场景复杂，存在大量例外情况
- 需要理解非结构化材料，如聊天记录、图片、物流说明
- 企业希望提升复杂案例处理质量，而不仅仅是追求固定规则执行
- 业务政策本身较复杂，且需要跨系统综合判断

### 4. 如果我是负责人，会更倾向于哪种方案

如果让我做选择，我会更倾向于<strong>方案 C：Workflow + Agent 的混合方案</strong>，而不是完全选择 A 或 B。

原因是：

- 单纯使用 Workflow，虽然稳，但容易僵化。
- 单纯使用 Agent，虽然灵活，但风险与不确定性较高。
- 混合方案既能利用 Workflow 的稳定性与可控性，又能利用 Agent 的灵活分析能力。

### 5. 可行的方案 C

一个合理的方案 C 可以是：

- 用 `Workflow` 处理绝大多数标准退款案例。
- 当遇到规则无法覆盖、信息不完整、风险较高或用户争议较大的案件时，再交给 `Agent` 辅助分析。
- `Agent` 可以负责阅读政策、总结证据、生成建议结论和风险说明。
- 最终审批权仍可根据风险等级由人工或固定规则保留。

例如可以设计成三层：

- 第一层：规则引擎自动处理低风险标准单
- 第二层：智能体对复杂案例做分析和建议
- 第三层：人工审核高金额、高争议、高风险案例

这种设计本质上是让 Agent 成为“增强型决策助手”，而不是毫无约束的全自动审批者。

## 第 4 题参考答案

本题重点在于思考如何扩展 `Thought-Action-Observation` 循环。

### 1. 添加“记忆”功能

设计思路：

- 在智能体状态中增加一个 `memory` 模块，用于保存用户偏好，如预算、偏好景点类型、是否喜欢室内活动等。
- 每次对话结束后，从用户输入和交互结果中提取偏好信息，写入记忆。
- 在下一轮构建 Prompt 时，把与当前任务相关的偏好记忆注入上下文，让模型在推理时优先考虑这些信息。

例如可加入两类记忆：

- <strong>短期记忆</strong>：当前会话中的即时偏好，如“这次不想去太远的地方”。
- <strong>长期记忆</strong>：跨会话保存的稳定偏好，如“喜欢历史文化景点”“预算通常在 200 元以内”。

这意味着循环会从原来的：

`用户输入 -> Thought -> Action -> Observation`

扩展为：

`用户输入 -> 检索记忆 -> Thought -> Action -> Observation -> 更新记忆`

### 2. 门票售罄时自动推荐备选方案

设计思路：

- 在推荐景点后，增加一个“门票可用性检查”工具调用。
- 如果发现门票售罄，Observation 中返回“目标景点不可用”的结果。
- 模型根据这一反馈自动进入下一轮 Thought，重新筛选满足相似条件的备选景点。

实现上可以增加两个约束：

- 保留原推荐理由中的关键属性，如“历史文化”“适合晴天”“预算内”。
- 在重选时优先选择与原方案相近的候选项，而不是完全随机替换。

这样循环会变成：

`推荐景点 -> 检查库存 -> 若售罄则重新规划 -> 输出备选方案`

### 3. 用户连续拒绝 3 个推荐后反思并调整策略

设计思路：

- 在状态中维护一个 `reject_count` 计数器。
- 每当用户明确拒绝当前推荐时，计数器加 1。
- 当 `reject_count >= 3` 时，不再继续按原策略推荐，而是触发一个“反思”步骤。

反思步骤可以做三件事：

- 总结用户拒绝前面几个方案的共同原因
- 判断当前推荐策略是否过度依赖某类特征
- 主动向用户补充提问，或者切换推荐维度

例如，用户连续拒绝后，智能体可以输出类似的内部思路：

- 之前推荐过于强调热门景点，但用户可能更重视安静、小众或预算
- 当前信息不足，需要主动澄清用户更看重“距离、预算、体验类型”中的哪一项

因此循环可进一步扩展为：

`用户反馈 -> 更新拒绝计数 -> 达到阈值则反思 -> 调整策略 -> 继续推荐`

总结来看，本题的核心不是单纯增加工具，而是让智能体拥有更完整的<strong>状态管理能力、异常处理能力和策略反思能力</strong>。

## 第 5 题参考答案

下面以<strong>医疗诊断助手</strong>为例说明“系统 1”和“系统 2”的协同。

### 1. 哪些任务应由“系统 1”处理

“系统 1”强调快速、直觉式、模式识别式处理，因此适合：

- 对医学影像、化验指标或症状描述进行快速初筛
- 从大量病历文本中快速提取关键信息
- 基于历史案例快速匹配相似病例
- 对明显异常指标做出高召回率预警

例如：

- 看到胸片影像中明显阴影时快速提示“可能存在肺部异常”
- 在病历中迅速识别“高热、咳嗽、白细胞升高”等关键词组合

### 2. 哪些任务应由“系统 2”处理

“系统 2”强调缓慢、审慎、规则化和可解释推理，因此适合：

- 结合症状、病史、检查结果进行鉴别诊断
- 检查结论是否与医学指南、禁忌症和临床规则一致
- 对多种治疗方案进行风险收益分析
- 在高风险场景下生成结构化、可解释的决策依据

例如：

- 区分普通肺炎、病毒感染和其他肺部疾病
- 判断患者是否适合某种药物或治疗方案
- 根据指南确认是否需要进一步 CT、血检或专科转诊

### 3. 两个系统如何协同工作

一个可行流程如下：

1. `系统 1` 先进行快速感知和初步筛查，给出高召回率的候选异常、候选疾病和关键信息摘要。
2. `系统 2` 再对这些候选结果做规则校验、因果分析和多步推理，剔除明显不合理的结论。
3. 最终输出时，由 `系统 2` 生成更稳健、更可解释的诊断建议，并给出需要医生重点确认的依据。

这样的协同方式有几个优点：

- `系统 1` 提高效率，擅长从复杂数据中快速发现模式。
- `系统 2` 提高可靠性，擅长约束、验证和解释。
- 二者结合后，既能保持智能系统的敏捷性，又能减少纯直觉式模型带来的误判风险。

这正体现了神经符号主义的核心思想：让“直觉学习能力”和“规则推理能力”协同工作，而不是彼此替代。

## 第 6 题参考答案

### 1. 为什么智能体会产生“幻觉”

智能体产生幻觉，通常有以下几个原因：

- <strong>语言模型本身是概率生成模型</strong>。
  它的目标是生成“统计上看起来合理”的内容，而不天然保证事实为真。
- <strong>训练数据存在噪声和不完整性</strong>。
  如果模型在训练中学到的是不准确或冲突的信息，就可能在推理时生成错误内容。
- <strong>上下文不足或任务约束不清</strong>。
  当外部信息不够时，模型可能会用看似合理的语言去“补全空白”。
- <strong>工具调用或外部环境反馈出错</strong>。
  智能体不仅依赖模型，还依赖工具、API 和检索结果，一旦这些环节错误，最终结论也可能错误。
- <strong>多步推理中的误差累积</strong>。
  智能体任务往往是链式执行，一步判断偏了，后面可能继续沿着错误路径推进。

因此，智能体的幻觉并不只是“模型胡说”，也可能是“模型 + 工具 + 过程”共同导致的系统性问题。

### 2. 如果没有最大循环次数限制，会出现什么问题

如果没有最大循环次数限制，智能体可能出现以下问题：

- <strong>死循环</strong>：不断重复相似的 Thought 和 Action，始终无法收敛。
- <strong>资源浪费</strong>：持续消耗 token、API 费用和执行时间。
- <strong>错误放大</strong>：基于错误 Observation 反复行动，导致问题越来越偏。
- <strong>工具滥用</strong>：对外部接口进行无意义的高频调用，甚至触发限流或风险控制。
- <strong>用户体验变差</strong>：任务迟迟不结束，用户无法得到明确答复。

因此，设置最大循环次数本质上是一种<strong>安全约束与熔断机制</strong>，用于控制失控风险。

### 3. 如何评估一个智能体的“智能”程度，准确率是否足够

仅使用准确率<strong>远远不够</strong>。

原因是智能体不是只输出一个答案，它还要经历感知、规划、工具调用、执行和纠错等完整过程。因此，对智能体的评估应该是多维度的。

常见评估维度包括：

- <strong>任务成功率</strong>：是否真正完成目标
- <strong>准确性</strong>：结果是否正确
- <strong>效率</strong>：用了多少步、多少时间、多少 token
- <strong>工具使用能力</strong>：是否能正确选择和调用工具
- <strong>鲁棒性</strong>：面对异常输入、工具报错或环境变化时是否仍能稳定工作
- <strong>纠错与恢复能力</strong>：出现问题后能否自我修正
- <strong>可解释性</strong>：其决策过程是否清晰、可审查
- <strong>安全性与对齐性</strong>：是否会执行危险操作，是否符合人类目标和规则约束

如果只看准确率，会忽略很多关键问题。例如，一个智能体虽然最终答对了，但可能耗费了几十步、调用了很多无效工具、甚至中途做出过危险尝试。从系统角度看，这样的智能体并不能算“足够智能”。

更合理的结论是：

- 准确率是必要指标，但不是充分指标。
- 智能体评估应采用<strong>结果指标 + 过程指标 + 安全指标</strong>相结合的方式。
